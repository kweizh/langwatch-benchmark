## What the script does

1. **Reads the run-id** from `/logs/artifacts/run-id` and uses it in trace names (`Batch_RAG_${run-id}`) and the output filename.
2. **Parses the CSV** with `csv.field_size_limit(sys.maxsize)` to handle extremely large fields (the test CSV has a 132,031-character field).
3. **For each row**, creates a LangWatch trace named `Batch_RAG_{run-id}`, with a nested span named `Retrieval` of type `rag_retrieval`.
4. **Logs** the `query` as the span's input and the `retrieved_context` (truncated to 10,000 characters) as the span's output.
5. **Adds a client-side `exact_match_eval` evaluation** to the span — passes (score 1.0) if `generated_answer` is found as a substring within `retrieved_context`, otherwise fails (score 0.0).
6. **Outputs a summary JSON** file with `total_processed`, `total_passed`, and `total_failed`.

## Key implementation details

- **CSV field size limit**: Increased via `csv.field_size_limit()` with a fallback loop to handle platform-specific `OverflowError`.
- **1MB body size limit**: The `retrieved_context` is truncated to 10,000 characters before being logged to the LangWatch span, preventing HTTP 413 errors.
- **Dependencies installed via `uv`**: `langwatch`, `pandas`, and `tqdm` (required by the LangWatch SDK).
- **`${run-id}` template substitution**: The script substitutes `${run-id}` in the `--output` filename with the actual run-id read from the artifacts file.
- **Error resilience**: Each row's LangWatch trace creation is wrapped in a try-except so a single failure doesn't crash the entire batch. The evaluation result is computed client-side before the trace, so counts are always accurate.
