### How it works

**`configure_langwatch(tracer_provider)`** calls `langwatch.setup()` with:
- `tracer_provider` — the *existing* global provider (LangWatch sets `_is_dedicated_provider=True`, which causes it to call `provider.add_span_processor()` to add its own `FilterableBatchSpanProcessor` **without** replacing the global provider or touching pre-existing processors).
- `span_exclude_rules` — two `SpanProcessingExcludeRule` entries:
  - `span_name` exact_match `GET /health_check`
  - `span_name` starts_with `db.`
- `api_key` / `endpoint_url` read from `LANGWATCH_API_KEY` / `LANGWATCH_ENDPOINT` env vars (no hardcoded credentials).

LangWatch's `FilterableBatchSpanProcessor.on_end()` checks each span against the exclusion rules and **drops** matching spans *before* batching/exporting to the OTLP endpoint. Non-matching spans are exported normally. Other processors on the same provider (e.g. `ConsoleSpanProcessor`) still receive **all** spans because they are independent processors.

**`run_pipeline(query)`** uses `opentelemetry.trace.get_tracer(__name__)` (the global tracer) to emit 5 nested spans under a `rag_pipeline` root: `GET /health_check`, `db.query.documents`, `rag.retrieve`, `llm.generate`. Returns a non-empty answer string.
