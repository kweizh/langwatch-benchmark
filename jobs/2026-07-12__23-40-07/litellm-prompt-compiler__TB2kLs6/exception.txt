# Versioned Prompt Compiler with LiteLLM Execution and Trace Linkage

## Background
You are building the generation service for a customer-support platform that manages its prompts in [LangWatch Prompt Management](https://langwatch.ai/docs/prompt-management/getting-started). At runtime the service must fetch a **specific pinned version** of a prompt with the LangWatch Python SDK (`langwatch.prompts.get`), compile it with several dynamic template variables, and execute it through the [LiteLLM](https://docs.litellm.ai/) `completion` API using the prompt's own model identifier and compiled messages. The whole generation must run inside an **active LangWatch trace** so the LLM call is linked to the prompt and is observable.

The deployment target is a locked-down / CI environment: the prompt is already materialized locally (LangWatch *Guaranteed Availability*), and there are no live LLM credentials. Your service must therefore be deterministic and offline-capable while still exercising the real `langwatch` and `litellm` packages (no mocking of the SDK).

A pre-provisioned LangWatch prompts project already exists in the project directory: `prompts.json`, `prompts-lock.json`, and a materialized, versioned prompt for the handle `support-triage-agent`. Your job is to implement the generation service `run.py` on top of it.

## Requirements
- Load the prompt for a given handle through the LangWatch Python SDK (`langwatch.prompts.get`), honoring a caller-supplied version.
- Compile the prompt with multiple runtime template variables and execute the compiled messages through LiteLLM's `completion`, routing to the model declared by the prompt (the provider-prefixed identifier such as `openai/...`).
- Run the retrieval + compilation + completion inside an active LangWatch trace, and emit an inspectable local trace artifact proving the LLM execution span is nested under the trace root span (a single shared trace id).
- Implement non-trivial validation:
  - **Version integrity:** because a locally materialized prompt is returned regardless of the version requested, the service must verify that the version actually resolved matches the caller's requested version and fail loudly on any mismatch.
  - **Template variables:** every `{{variable}}` placeholder referenced by the prompt must be supplied; a missing variable must fail loudly and must not produce a successful result.
- Read all credentials/config strictly from environment variables. Do NOT mock LangWatch, LiteLLM, their HTTP clients, or any transitive dependency — the real packages must be installed and importable.

## Implementation Hints
- Install Python packages with `uv` (`uv venv`, then `uv pip install ...`). The `langwatch` and `litellm` packages are required.
- Run the service with the project root as the working directory so the SDK can auto-discover the materialized prompt under `./prompts/.materialized/`. See [Guaranteed Availability](https://langwatch.ai/docs/prompt-management/features/advanced/guaranteed-availability) and the [Prompts CLI](https://langwatch.ai/docs/prompt-management/cli).
- Compile the prompt with the SDK's compilation API; prefer the strict-compilation variant so missing template variables raise instead of silently passing through.
- Pass the prompt's own model string unchanged to LiteLLM (do not strip the provider prefix). Since there are no live LLM credentials, drive `completion` deterministically with LiteLLM's mock-response mechanism so no network/API key is needed while still exercising the real `completion` code path.
- Establish the LangWatch trace with `langwatch.setup()` plus a trace boundary. To make trace linkage inspectable offline, capture the emitted OpenTelemetry spans in-process (e.g. attach your own `TracerProvider`/span exporter to the LangWatch setup) and serialize the stable span fields (name, trace id, span id, parent span id) to the trace artifact.
- Keep machine-readable output in files (not stdout), because LangWatch/LiteLLM emit their own log lines.

## Acceptance Criteria
- Project path: /home/user/myproject
- Command: `python run.py --handle <handle> --vars <json_object> [--version <int>] --out <path>`
  - `--handle`: the prompt handle to load.
  - `--vars`: a JSON object string mapping template-variable names to string values.
  - `--version`: optional integer version; when provided the service must confirm the resolved prompt is exactly that version, and when omitted the version recorded in the prompts lock file is used.
  - `--out`: path where the compiled result JSON is written.
- On success (exit code 0) the `--out` file must contain a JSON object with this shape:
  ```json
  {
    "handle": string,
    "version": integer,
    "model": string,
    "trace_id": string,
    "messages": [ { "role": string, "content": string } ],
    "response": string
  }
  ```
  - `model` is the provider-prefixed model string taken from the prompt and passed to LiteLLM (begins with `openai/`).
  - `version` is the resolved integer version.
  - `trace_id` is the non-empty lowercase 32-hex-character OpenTelemetry trace id of the active trace.
  - every message `content` has all placeholders substituted; no `{{` substring may remain.
  - `response` is the non-empty text returned by the LiteLLM `completion` call.
- Trace artifact: on success the service also writes `/home/user/myproject/trace_spans.jsonl`, one JSON object per line describing a captured span with at least the fields `name`, `trace_id`, `span_id`, `parent_span_id`. It must contain a span named `llm_generation` (the LLM execution) whose `trace_id` equals the result `trace_id`, and whose `parent_span_id` refers to another captured span sharing that same `trace_id` (i.e. the LLM span is nested under the trace root span).
- Error handling (must exit non-zero and must NOT write a successful `--out` result):
  - If `--version` is supplied but does not match the resolved prompt version, fail and report a version mismatch.
  - If any template variable required by the prompt is missing from `--vars`, fail and name the missing variable.
- Required pre-existing artifacts at the project root (already provisioned): `prompts.json`, `prompts-lock.json`, and `prompts/.materialized/support-triage-agent.prompt.yaml`.
